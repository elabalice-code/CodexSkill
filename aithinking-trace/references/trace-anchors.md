# 双焦点 Trace：消费端锚点与准星

取得产生核心效果的配置后，两端源码都已解除 Pending：消费端有了调查方向，生产端有了输入对照价值。本文件用于双焦点日志诊断的准备与追踪，消费端按“副锚点 × 2 → 主锚点 × 1 → 日志缺口 → 准星”的顺序推进。

## 1. 两个副锚点：正式消费动作前后的信号集中区

选择类似面向切面编程观察切面的“神经信号”高度集中区。这些位置能够观察大量关联数据，但位置必须围绕实际消费动作：一个在正式消费前，一个在正式消费后。

| 副锚点 | 观察内容 | 作用 |
| --- | --- | --- |
| 消费前 | 进入消费动作的信号、关键属性、状态及交接信息 | 确认实际送到消费者面前的输入 |
| 消费后 | 消费结果、输出、状态变化及后续交接 | 确认消费动作实际产生了什么 |

两端记录应能关联到同一次消费。不要只挑日志多的公共函数，也不要把整个系统启动与退出当成这两个位置。存在异步消费时，“消费后”指实际消费完成后的观察位置，不能把提交任务后立即返回当成消费完成。

副锚点能观察大量数据，不意味着把所有数据都打印出来。优先保留能够解释配置前后差异的字段。

## 2. 一个主锚点：真正产生执行差异的位置

结合副锚点的输入与结果对照，在消费处理范围中选择一个暴露执行分歧的主锚点：

- 面向过程结构：大量 if-else 中使执行路径分开的判断、返回或丢弃分支。
- 面向对象结构：信号消费与执行分派中，决定信号由谁处理、是否处理及走向哪个行为的位置。

主锚点的路径日志要明确说明执行经过了哪些选择，尤其是“抛弃信号”“未能走向正确路径”的位置与当时的关键条件。只打印“进入函数”“处理失败”不足以暴露这种差异。

副锚点给出正式消费前后的整体数据视野，主锚点给出其中的执行路径差异。主锚点是当前定位手段，不自动等于根因所在。

### 区分判定、动作和最终效果

每条日志只能声称它实际观察到的事实：

| 观察点 | 能直接证明 | 不能据此直接宣称 |
| --- | --- | --- |
| 过滤器、校验器等返回值 | 本次判定的返回结果 | 调用者已经投递、丢弃或完成业务 |
| 实际入队、提交或放弃动作之后 | 指定消费者的该次动作已执行 | 异步下游已完成消费，或所有消费者均丢失该信号 |
| 终端处理与外部状态 | 对应业务结果或目标表现 | 未被记录的内部指令及失败原因 |

将动作证据放到实际调用之后；可能失败的调用还需核对其返回状态。过滤放行后可能继续因资源、复制、裁剪或提交失败而放弃，不能把前置成功写成最终成功。保留前置返回值作为辅助点，再用动作点区分后续失败原因。

有引用计数、克隆或所有权转移时，释放旧引用不等于业务信号被丢弃。例如原对象释放后，其克隆仍可成功入队。按当前消费者最终交接结果分类，并在对象失效或转移前保存日志所需的标量与关系键；动作后输出日志时不能再解引用已释放对象。

### 只记录原生 gate，不用诊断代码重演业务流程

路径中的每个标记应能对应未插桩程序已有的条件、实际调用或返回分支。诊断代码为选择样本而额外解析出的字段可以作为辅助数据，但不能命名成业务程序已经通过的 gate，更不能用另一次计算代替原调用结果。

例如诊断工具可以读取完整对象，而原程序只能访问受限视图；“诊断读到目标字段”不能证明原生读取成功，也不能证明后续字段比较已执行。应记录原操作的访问范围、返回值与实际分支，再依据当前程序映射字段含义。日志选择条件若依赖正在调查的失败操作成功，会恰好漏掉失败样本，应改用调用上下文或更宽但有界的筛选。

对规则引擎、解释器、JIT 或生成代码，区分规则构造/安装位置和逐次执行位置。查明当前运行模式的真实调用链，核对实际运行的程序身份及展开后的指令；安装时打印不能证明逐条运行路径，JIT 开启也不自动排除共享函数。共享函数没有业务上下文时，仅记录它真实拥有的数据，再由调用者日志关联，避免在底层重新实现业务识别。

## 3. Path `->` 日志记录规则

一次函数调用维护一份局部路径，沿真实执行顺序追加标记，在实际出口输出一次。`->` 表示本次调用内已观察到的先后关系，不表示耗时、完整调用栈或跨线程因果关系。分支里只累计路径和必要标量，不逐分支打印。

### 标记放在哪里、写什么

| 位置 | 标记规则 | 示例 |
| --- | --- | --- |
| 入口 | 初始化本次调用的路径 | `ENTER` |
| 原生条件分支内部 | 条件已完成求值，记录实际选择的一侧 | `VALID_OK` / `VALID_FAIL` |
| 操作调用返回后 | 根据原返回值区分成功和失败 | `ACTION_OK` / `ACTION_FAIL` |
| 清理动作之后 | 仅在该动作实际完成后记录 | `CLEANUP_DONE` |
| 实际返回之前 | 记录即将返回及返回值；不声称返回已经完成 | `RETURN`，返回值另列字段 |

标记应短、含义稳定，能直接定位到源码中的追加点，避免只有 `A->B->C` 或模糊的 `OK->FAIL`。只在需要区分调用未返回时，增加 `CALL_BEGIN` 与返回后的标记；不能在动作之前写 `DONE`。不为生成路径再次调用业务函数或重新求值有副作用的条件，也不在出口根据最终结果反推、补造整条路径。

各条路径初始化和追加语句旁保留可搜索的 `PathMark` 注释，例如 C/C++ 的 `// <--   PathMark`；其他语言使用其合法注释语法。它是源码定位标记，不是运行时路径节点。对宏或包装函数，标记调用位置，使每个运行时节点都能追溯到具体原生分支。

### 调用隔离、有界累计与单次输出

- 路径缓冲区和截断状态属于本次调用。不得共用可写全局缓冲区；递归也要隔离。异步交接通过显式上下文或关联键连接，不继续引用已经退出函数的局部缓冲区。
- 使用有界追加，维护当前位置和容量，避免无上限增长或反复扫描整串。完整追加不了一个节点时停止追加，保留此前完整节点，并用独立的 `truncated=1` 字段明确说明；不要让半个节点被当成真实路径。
- 循环按诊断需要记录有限次数的分支，并附迭代数或省略标志。压缩重复节点会丢失顺序信息，需要逐次顺序时改为有界采样，不能假称记录完整。
- 正常返回、错误返回和原有异常路径都应覆盖。能保持原语义时汇合到一个日志出口；不适合汇合时保留原出口，保证每次调用至多输出一次。不要为凑单出口改变返回值、异常传播、锁、所有权及清理顺序。
- 用同一次日志调用输出关联键、结果、截断状态和 `Path`。可以将 `Path` 放到同一条日志的下一行，但不要拆成第二次打印；日志系统不支持多行原子记录时保持单行。具体字段大小写沿用项目约定。

高频路径另设样本范围和输出预算；入口选定的样本应尽量覆盖其失败出口，避免只保留成功调用。不同观察点各自限前 N 次，不保证覆盖相同信号；限流、截断和采集丢失都属于观测缺口。日志不应通过重排数据、额外消费、修改裁决结果或改变交接路径来制造成功。

### 通用伪代码

以下假定被观察函数原本就有校验、执行和对应返回分支，仅演示插桩位置；`PathBuffer`、`append`、`emit_one_record` 是伪接口。`append` 只做有界累计并设置截断状态，不打印；实际实现使用目标环境合适的工具，不照抄接口名。

```text
function process(input, call_id):
    path = PathBuffer("ENTER")                   // <--   PathMark

    if not validate(input):                     // 原有判断，仅执行一次
        path.append("->VALID_FAIL")             // <--   PathMark
        result = INVALID
        goto out

    path.append("->VALID_OK")                   // <--   PathMark
    result = perform(input)                     // 原有动作，仅执行一次
    if result == SUCCESS:
        path.append("->ACTION_OK")              // <--   PathMark
    else:
        path.append("->ACTION_FAIL")            // <--   PathMark

out:
    path.append("->RETURN")                     // <--   PathMark
    emit_one_record(call_id, result, path.truncated, path.text)
    return result
```

可能输出的三条记录分别来自三次调用：

```text
call=101 result=INVALID truncated=0 Path="ENTER->VALID_FAIL->RETURN"
call=102 result=SUCCESS truncated=0 Path="ENTER->VALID_OK->ACTION_OK->RETURN"
call=103 result=ERROR   truncated=0 Path="ENTER->VALID_OK->ACTION_FAIL->RETURN"
```

`ACTION_OK` 只表示原操作返回了成功；若操作只是异步提交成功，它不能证明后续业务完成。读路径时从入口找第一个分歧，再结合返回值和关联记录解释原因，不能将未执行的分支补入路径。

### 出口日志的覆盖边界

仅在出口打印无法保留崩溃、强制终止或永久阻塞前的局部累计路径。没有出口记录不能直接解释为函数未进入。若当前问题就是无法到达出口，按具体疑点补充进入/完成检查点或外部追踪，并明确这是为弥补出口观测盲区的例外；不要因此给所有正常分支增加打印。

## 4. 从日志缺口确定真正的准星

主副锚点会覆盖绝大部分相关日志，但仍存在缺口。完成这组布点后，继续查找输入、输出和路径之间尚无法解释的部分，不能因已有三个锚点就宣布覆盖完整。

将同一信号的生产端记录、两个副锚点和主锚点路径对齐，比较产生核心效果的配置改动前后：哪里已被日志解释，哪里仍缺少足以连接前后行为的信息？

缺口可能表现为消费前有记录而消费后缺失、主锚点路径进入某段处理却没有解释后续选择，或两端关键属性发生变化但中间没有对应记录。此时先区分实际执行缺口与日志未覆盖、关联失败、截断等观测缺口，不能仅凭“没有日志”就判定信号在那里被丢弃。

沿具体缺口做最小范围的源码追踪或补充观察，再对齐结果。逐步把焦点缩到能够解释信号丢弃、路径偏离或关键状态差异的具体条件、调用或交接位置，这才是最终要确认的“准星”。

记录从哪一处日志缺口追到该位置，以及哪些数据和路径支持这个定位。缺口尚未解释时，保留候选准星；不要把猜测写成已确认结果。

使用现成 tracepoint 或探针前，查清触发条件和覆盖范围。例如某些释放事件仅在引用计数归零时触发，缺少事件不能证明调用者未释放引用；inline 动作也可能没有独立可探测符号。必要时观察具体调用点。源码证明一条路径可达、旁路工具看到了数据，都不能单独证明目标消费者实际走过该路径；还需核对目标实例的绑定、注册或分派关系及运行记录。

## 5. 关联同一信号与同一次消费

先说明关系键标识的是哪一层身份，按跨层边界选择组合，不要求所有日志使用同一个字段：

| 身份 | 常见线索 | 使用边界 |
| --- | --- | --- |
| 事务或会话 | 请求号、事务号 | 一次事务可能包含重试、多个响应或多条数据 |
| 单条信号内容 | 序号、长度、内容指纹 | 相同内容可能重复发送；非密码学校验值也可能碰撞 |
| 内存对象 | 对象地址或稳定对象标识 | 对象会克隆、替换或复用；只在明确生命周期内关联 |
| 消费实例与调用 | 订阅者/队列/程序身份、调用序号、执行上下文 | 同一信号可以进入多个消费者，同一对象也可被多次处理 |

将跨层内容关系键与局部调用关系键连接起来。发生克隆或转换时保留输入标识及转换关系；有并发或重复执行时补足能区分调用的上下文，不能只按日志相邻或地址相同拼接。底层日志无法唯一归属某次消费时，明确关联歧义，不能挑选符合假设的一条结果。

指纹对照需约定相同的字节范围、算法和有效状态，计算失败不能当作有效的零值。内容被合法改写时，记录转换关系或选择仍保持不变的范围，不能把指纹不同直接判为损坏。事务号、长度和内容指纹的组合能增强同一信号的证据，但不应命名为全局唯一身份。

## 6. 同时比较内容与表示形式

数据内容一致不等于消费者能够按其访问方式读取。生产侧与消费侧除内容外，还应按候选机制记录表示形式和元数据，例如有效范围、编码、偏移基准、对齐、所有权或状态。只选会影响当前消费条件的属性。

将原生访问请求与可用范围直接对照。例如某字段存在于完整对象中，但不在当前视图的有效范围内，就不能由字段存在推定本次读取成功。静态边界分析提供可检验预测，实际失败仍以真实访问分支和返回值确认。

对照实验中同时回答：内容是否变化、表示形式是否变化、原生分支如何变化、最终消费者动作与外部效果是否变化。这样才能把“改参数后恢复”推进为可解释的生产—消费关系，而不是把所有差分都归结为数据损坏。

## 诊断记录

保留生产端焦点、两个副锚点、一个主锚点各自的职责和位置，说明信号如何关联、路径日志如何在出口一次输出，以及缺口如何引导到准星。只准备了方案时标为待采集；已有日志时据实报告覆盖与缺口，不补造执行结果。

对关键结论紧邻写出证据边界，可用“结论｜源码/运行记录位置及版本｜关系键及作用域｜直接观察或推导｜剩余缺口”记录。不要为了补齐表格重复采集已有证据。

判读时可用以下反例自检：

- 前置校验通过而随后入队失败：只能报告校验通过及实际失败动作，不能称交接成功。
- 原对象释放而克隆入队：按该消费者交接成功记录，不能只因调用释放函数就判为丢弃。
- 诊断解析成功而原生读取报错：字段存在与访问失败可以同时成立，不能伪造业务比较路径。
- 相同事务号或对象地址对应多个样本：补足信号与消费调用关系，歧义未解时不声称同一次消费。
- 插桩已上传但尚未部署采集：可以报告设计和静态预测，不能将预计路径写成运行结论。
