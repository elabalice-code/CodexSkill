# AIThinking-Trace

将目标问题逐步收敛到唯一闭环动作：第零步排除噪声，第一步拆分四领域，第二步从动作焦点推导消费路径焦点，第三步逆向回溯并做配置测试，第四步解禁两端并通过双焦点 Trace 定位准星，第五步确定生产端或消费端的修正方向。

本技能组织分析，不以编写或修改代码为默认任务。对用户指定的已验证 golden example，接受其事实与结论，提炼分析流程。

**强制交付：每次调用本技能，都必须生成或更新并交付本次调查的可编辑 `.drawio` 流程图。** 流程图是判断调查方向是否合理的主要交付物，文字说明、截图或 Mermaid 不能替代它。调用开始时读取 [references/drawio-output.md](references/drawio-output.md)，分析过程中维护图，结束时提供实际文件链接。调查尚未闭环也必须交图，并如实标明 Pending、证据缺口与下一步。

示例中的已确认结论属于该示例。应用到正在调查的项目时，按该项目最新状态记录已观测事实与待验证机制，不从示例继承“已经取证完成”的状态。

## 第零步：排除常见噪声因素

先明确目标问题及其发生场景，再识别足以干扰问题判断的常见因素，避免把环境限制或不合适的观测对象误判为目标系统故障。

例如：分析国内设备无法联网时，不能仅凭无法访问 Google 就认定设备网络链路有故障；先区分外部访问限制与设备自身的联网问题。

根据已有材料或小范围验证，将相关噪声因素分为已排除、已确认影响目标、尚未明确。记录简短依据。用户已确认的案例事实可以直接作为依据，不重复验证。

- 已排除的噪声不继续占用主分析路径。
- 已确认影响目标的因素属于实际问题或前置条件，不能因“常见”而忽略。
- 尚未明确的因素保留状态，不伪装成已排除；只补充能够区分它与目标故障的必要信息。

噪声检查围绕当前场景展开，不扩张成穷举式环境检查清单。不存在相关噪声时，简述后进入第一步。

## 第一步：基于思维定式拆成四个领域

采用固定的生产与消费分析框架，在尚未确定故障位置时，先展开四个调查领域。它们来自既有思维定式，不是实验之后才得出的结论，也不是四个故障假设。

| 领域 | 类型 | 要理解的内容 | 初始处理 |
| --- | --- | --- | --- |
| 生产终端节点 | 源码领域 | 信号由谁产生，源头实现及输出是什么 | 改动通常很小，早期调查价值低，暂置 Pending |
| 动作路径分析 | 验证领域 | 目标行为怎样发生，各阶段实际出现什么动作与结果 | 优先从已有记录或可行验证取得突破 |
| 信号消费路径分析 | 验证领域 | 信号经过哪些节点、交接与处理，最终如何到达消费者 | 建立链路并寻找能够观测和验证的节点 |
| 消费终端节点 | 源码领域 | 谁最终消费信号，其内部实现怎样完成预期功能 | 标识承担者和范围；宽泛源码调查暂置 Pending |

四个领域都要保留。材料不足时标注尚不明确的承担者或路径，不编造节点，也不省略整个领域。

### 两个源码领域：先圈定，暂缓深入

两端 Pending 的原因不同：生产端源码改动通常很小，早期直接调查对定位问题的价值低，因此先 Pending；消费端 Base 的源码领域很大，尚无焦点时调查范围过宽，因此先 Pending。不要将两端统一解释为规模大。

Pending 表示当前阶段暂缓投入，不代表已排除该领域或发现了缺陷。取得产生核心效果的配置改动后，按第四步解禁：消费端获得定向调查依据；生产端因能够提供与消费结果对应的输入证据，调查价值显现，也解除 Pending。随后准备双焦点 Trace。

若输入已包含这种定向证据，可据此缩小调查范围，不机械地重复等待。当前任务没有源码时，也可以先完成领域拆分和验证分析，不把获取全部源码作为起步条件。

### 两个验证领域：优先寻找突破口

动作路径关心“事情如何发生”，信号消费路径关心“信号如何流转”。不要将二者合并成一个笼统的日志分析领域。

- 动作路径：从已有日志、抓包、状态或复现记录中识别动作顺序、预期结果与实际表现。
- 信号消费路径：整理生产到消费的交接关系，标出可观察节点及尚未明确的位置，寻找可以区分候选方向的验证入口。

先利用已有材料；需要新验证时，提出具体观察对象及它能回答的问题。能从验证结果缩小源码调查范围，才构成突破。不要把“源码暂置 Pending”理解为整个分析停止。

## 第二步：从执行动作焦点推导信号消费路径焦点

两个验证领域之间存在推进关系：先在软件系统的执行动作路径中确认问题动作，再将它映射到软件信号消费路径中的一段范围。动作焦点帮助缩小信号调查范围，并不要求一步定位到单个函数或根因。

### 先观察 from start to end 的动作过程

分析 OS 日志时，观察范围必须覆盖与目标相关的一次完整执行过程，从初始化开始，沿后续动作向前推进，直到该次过程结束或故障结果出现。不能只截取报错附近或最新的几行日志，跳过前面的初始化和状态变化。

先沿 OS 日志建立动作过程，再结合场景常用分析工具补充观察。例如网络问题可从初始化、设备注册与发现、连接建立等动作往后分析，再用 TCPDump 等工具明确具体协议交互。该顺序用于建立上下文，不把某个工具的名字固化为所有问题的必选项。

已有记录若只覆盖局部，明确缺失的时间段或阶段，主动从可访问材料补查；确实无法获取时再指出需要补充的记录。局部日志仍可提供线索，但不能被表述为已覆盖完整过程。

沿过程定位问题动作，说明：此前发生了什么、当前应发生什么、实际发生了什么，以及日志或工具观测依据。不要仅凭出现一个错误关键字就跳过动作过程直接指定责任模块。

对同时出现的多条线索，按它们与目标异常的对应关系分配调查优先级：是否发生在相关动作阶段，是否随问题出现，是否能解释当前表现。保留暂未进入主线的观察及理由；偶发不等于无关，醒目的异常也不自动成为主线。

### 将问题动作映射到信号消费区段

对已经确认的问题动作，依次明确：

1. 该动作依赖或产生什么软件信号，例如报文、事件、请求或数据对象。
2. 谁产生该信号，它经过哪些传递与处理节点，由谁消费以完成动作。
3. 当前动作表现将调查指向哪一段交接或消费范围，映射依据是什么。

明确区分“动作路径中的焦点”和“信号消费路径中的焦点”：前者描述哪个执行动作出现问题，后者描述为完成该动作而参与的信号处理区段。一个问题动作可以指向多个连续节点或多个候选区段，不强行压缩成一对一映射。

输出带上下游上下文的消费链，并标明当前重点区段及其起止节点。范围外的节点不能仅因本次未聚焦就被判为正常；当前区段也不自动等于已经确定的故障责任方。

### 自主查明信号消费路径

当分析需要明确软件信号消费路径时，主动调查这条路径是什么，不以“路径未知”结束分析，也不默认要求用户先画好路径。

先利用已有图示、日志、工程资料与可访问的接口定义；不足时查阅相关源码、官方文档或上游实现，必要时自主联网调查。围绕当前信号和动作查清节点职责、交接关系与消费方向，不扩张成全系统源码阅读。

源码领域的 Pending 暂缓的是宽泛的内部故障调查，不阻止为建立消费路径而进行定向源码查询。路径调查与源码深查的范围应保持清楚。

对调查得到的路径，保留关键来源、适用实现或版本信息；区分当前系统已有证据确认的关系与根据通用实现推导的关系。仅在可访问材料确实不足时，指出具体缺口及其影响，不补造项目特有节点。

第二步的推进链为：

**完整动作过程 → 确认问题动作 → 确定相关信号 → 自主查明消费链 → 映射重点消费区段。**

## 第三步：定位消费者终端，由近到远回溯并做配置测试

确认信号消费路径后，优先定位消费者终端，以此作为逆向排查的锚点。沿消费关系从终端由近到远回溯候选 Block 点，再用针对性的配置变化观察系统反应。

### 找到负责最终裁决的角色

消费者终端是当前目标问题中，相关数据最终指向、并对数据是否正确或是否满足消费条件作出“裁决”的角色。它是否接受并完成消费，决定系统能否表现出目标所要求的正常样貌。

说明这个角色接收什么、依据什么条件接受或拒绝，以及它的消费结果如何关联目标的外部表现。以职责识别终端，不把图中最右侧节点、最后一条日志或展示结果的界面自动当成裁决者。可以先定位到承担此职责的子系统，不要求先读完其内部代码。

识别终端不等于认定终端有错，也不自动解除其整个源码领域的 Pending。它首先提供一个明确的排查起点：什么数据和条件能够让这个角色完成正常消费？

### 沿消费关系由近到远回溯候选 Block 点

从终端自身可观察的接收条件及紧邻它的交接开始，再向更上游的处理节点推进。这里的“近”和“远”指信号消费依赖上的距离，不是源码文件位置、日志时间先后或图形排版距离。

Block 点是可能使数据无法被最终正常消费的位置或条件，包括阻止交接、丢弃、过滤、错误处理或使数据不满足终端要求的环节，不仅指线程阻塞或死锁。

结合第二步得到的重点区段，按距消费者终端由近到远排列候选点。对每一点说明：它可能怎样影响终端裁决、有什么可调配置，以及可以观察到什么变化。先从近端可验证的候选开始；缺少可调配置时记录可用的观测方式，继续推进，不强行转为代码修改。

### 用配置变化试探候选点

围绕候选 Block 点“拉一拉、扯一扯、改一改”：调整阈值、开关、模式等实际存在的配置，观察消费结果和外部表现是否随之改变。测试必须服务于具体候选解释，避免无目标地同时改动多个配置。

把候选解释写成可被结果支持或削弱的假设，保留“候选点 → 假设 → 测试 → 观察结果 → 当前判断 → 下一步”的关系。假设节点与事实节点分开；无变化的分支保留测试条件与判断，后续没有新依据时不反复重开同一分支。

每次测试至少保留以下信息，可用紧凑表格记录：

| 候选 Block 点及假设 | 原配置与原表现 | 配置改动及实际生效情况 | 预期区分的问题 | 实际变化、当前判断与下一步 |
| --- | --- | --- | --- | --- |

在已有任务授权范围内执行可行测试。记录原值，尽量一次改变一个因素，必要时恢复原配置做对照，避免前一次改动混入下一次判断。仅分析已有案例时使用案例结果，不把拟议测试写成已执行。

对带缓存、会话或重试状态的系统，只恢复配置值不等于恢复实验起点。按场景重建会影响结果的状态，记录每轮起始条件与配置的实际生效值；适合时使用原条件 → 对照条件 → 恢复原条件的可逆实验。重置动作仍以当前授权为界，不把某种状态清理固化为通用命令。稳定差分用于收敛受影响的代码路径，不能单独证明具体失败指令；取得突破后转向第四步的机制取证。

- 结果无变化：确认配置已生效后，降低当前候选解释的优先级，继续向较远候选推进。
- 结果改善、恶化或发生其他相关变化：记录变化，把调查集中到受该配置影响的处理范围。
- 无法确认生效或无法观察结果：保留为未判定，不能当作“测试无效，候选已排除”。

重点同时观察局部信号处理和原目标的外部表现。某项配置改变了日志，不等于已经改变终端裁决；配置使目标恢复，则提供了继续缩小调查范围的重要依据。

已有多个测试从不同入口指向同一效果时，将它们汇入一个明确判断，说明共同指向的范围，并保留各测试到该判断的依据。不要把每次成功都另开成一个根因，也不要仅因入口不同就视为相互独立的证据。这是对已有结果的汇合方式，不要求每个候选都必须做多种测试。

第三步的推进链为：

**定位最终裁决者 → 由近到远排列候选 Block 点 → 针对配置做测试 → 观察消费与外部表现的变化 → 收敛下一轮调查范围。**

## 第四步：解禁消费端 Base 调查，先准备双焦点 Trace

当第三步找到产生核心效果的配置改动，例如使原先失败的目标恢复正常，就具备解除消费端源码调查 Pending 的依据。仅有无关日志变化不构成这里的核心效果。沿用已确认的配置与效果记录，不另起无关验证流程。

此时的顺序是：**解禁消费端调查 → 暂缓深入 → 回看生产端，其价值显现并解除 Pending → 准备双焦点 Trace 日志诊断。** 不因获准调查消费端就立即单向钻入其内部实现。

### 识别作为背景的消费端 Base

这里的消费端源码不限于 OS 或系统源码，也可以是应用的架构代码、框架或小型产品的基础实现。它在当前问题中扮演软件产品的“背景”与 Base，承接生产端送来的信号，并通过消费行为决定外部结果。

Base 是相对于当前新增功能和信号关系的角色，不由代码规模、仓库位置或是否属于操作系统来决定。它是背景不代表它必然正确；配置变化产生核心效果，也不等于已经判定 Base 单方有错。

解禁后先圈定与有效配置相关的消费入口、裁决位置或处理区段，作为日志诊断的消费端焦点，不把整个 Base 展开为全面源码审查。

### 立即回看生产端代码

重新唤起对生产端的认识：通常是新加入的驱动、应用，或小型项目新增的模块代码、业务代码，源码改动一般很小。早期它的调查价值低；现在有效配置已将消费问题聚焦，生产侧输入可与消费侧的执行差异对照，因此价值显现，解除生产端 Pending。明确这段代码生产什么信号、怎样构造或组织它、通过哪里交给 Base，以及有效配置可能改变哪部分生产或交接行为。

优先利用前面已知的源码位置和接口；需要时做定位焦点所需的定向查看。生产端可能与 Base 位于同一仓库甚至同一模块，仍按生产与消费职责区分。

这次回看是为了把两个源码领域同时放回诊断视野：一端提供了什么，另一端怎样消费和裁决。不能只保留消费端焦点，也不能仅因生产端是新增代码就预设它有错。

### 准备生产端与消费端的双焦点 Trace

双焦点指同一条问题信号链上的两个诊断视角，不是第二步的“动作焦点与消费路径焦点”。围绕取得核心效果的配置，准备能够关联两端记录的日志方案：

| 焦点 | 日志应回答的问题 | 选点方向 |
| --- | --- | --- |
| 生产端 | 实际构造并送出了什么，交接时处于什么状态？ | 信号构造、关键属性形成、提交给 Base 的位置 |
| 消费端 Base | 实际收到什么，在哪个条件或分支接受、拒绝或改变了处理？ | 对应的接收入口、消费条件、裁决结果或返回位置 |

为两端选择能够关联同一份数据、同一次请求或同一轮动作的线索，例如已有请求标识、序号或可对应的事件信息。时间戳可用于辅助对齐；信号经过复制或转换时说明关联方法，不默认对象地址始终不变。

准备比较配置改动前后的关键数据属性、状态和分支结果，并把两端表现对应回原目标的外部表现。日志字段与有效配置所影响的候选机制相关即可，不要求全面打印或为所有项目固定同一套字段。

### 消费端按主副锚点追踪，再从缺口确定准星

消费端源码范围大，按顺序组织追踪：**正式消费前后的副锚点 × 2 → 执行分歧处的主锚点 × 1 → 根据日志缺口确定真正的准星。**

- 两个副锚点：选在正式产生消费动作之前和之后的信号高度集中区，类似面向切面编程的观察切面，能看到丰富的关联数据。
- 一个主锚点：选在真正产生执行差异的位置，以路径日志暴露丢弃信号、未进入正确路径等分支。面向过程代码关注 if-else 分歧，面向对象代码关注信号消费与执行分派。
- 轻负载路径日志：分支中尽量用 `->` 拼接路径，每次函数调用只在实际出口落一次累计日志，避免沿途反复打印。
- 准星：主副锚点能覆盖绝大部分相关日志，但仍有缺口；沿缺口定向补查，确定真正需要聚焦的具体位置，不能把主锚点直接等同于最终准星。

准备或开展这部分诊断时，读取 [references/trace-anchors.md](references/trace-anchors.md)，按其中的锚点选择、轻负载日志和缺口追踪方法推进。编写 Path 日志时按其第 3 节执行：调用内有界累计 `->` 标记、源码追加点标注 `PathMark`、实际出口单次输出，并处理截断和未到达出口的观测边界。

选点时区分原生判定、已执行动作和诊断附加读取：判定返回值不能直接冒充入队、释放或业务完成；路径标记只对应原程序实际经过的分支。跨层关联还要区分事务、单条信号、内存对象与消费调用，核对内容及其布局、状态是否同时满足消费条件。具体证据边界和反例见上述锚点细则。

第四步交付双焦点诊断准备及锚点追踪依据：有效配置及效果、两端解禁原因、生产端焦点、消费端两个副锚点和一个主锚点、日志关联与对照方式，以及已识别的日志缺口和准星依据。区分计划、实际日志及已定位结果；尚未采集日志时不声称已经找到缺口或准星。

## 第五步：依据最终准星，确定修正方向并收口

定位最终准星后，修正方向一般有两个：改生产端，或改消费端。结合双焦点记录和准星所揭示的机制，判断应该在哪一侧改变行为，使信号走到正确消费路径并恢复原目标。

准星是暴露问题机制的位置，不必然就是最终需要修改的位置。例如在消费端看到信号被丢弃，可能是生产端构造的数据不满足约定，也可能是消费端对输入的处理存在缺陷。以两端的实际关系选择修正侧，不因生产端通常改动小就默认改生产端，也不因异常在 Base 中显现就默认改 Base。

### 方向一：修改生产端代码

当准星及两端对照指向信号构造、属性设置、提交方式或交接行为时，明确生产端需要修改的具体位置、行为，以及该修改如何使信号满足消费条件。

生产端通常是新增驱动、应用、模块或业务代码，改动往往较小。将修正聚焦到已定位的信号生产与交接关系，不扩张成无关重构。

若生产侧调整是在适配某个消费端版本或规避已知消费缺陷，说明这一适用条件，不把规避方式写成生产端原本一定存在错误。

### 方向二：修改消费端代码或处理 Base 版本

消费端改动通常较重，需按产品 Base 的实际形态展开：

| 消费端形态 | 收口方向 | 应明确的内容 |
| --- | --- | --- |
| 个人小型应用、自有架构代码 | 修正消费逻辑；必要时调整架构 | 准星暴露的消费规则、分派或职责问题，以及需要改变的具体关系 |
| 大型 OS、外部系统 Base | 检查实际 OS 版本、相关实现与修复状态，确定适用的版本或补丁处置 | 问题对应的版本条件、当前实现是否包含修复，以及可行的升级、补丁或兼容安排 |

小型应用不因选择消费端方向就必然需要重构；大型 OS 也不以笼统的“改内核”结束。沿准星对应的机制调查版本和修复，必要时自主查阅上游资料。核对实际构建及相关补丁是否存在，不能仅凭主版本号推定行为。

### 汇成唯一闭环动作

给出当前问题应采取的具体方向、修改或处置对象、适用条件，以及它如何回应最初目标。不要把“改生产端或改消费端”两个未决建议并列作为最终结论；证据尚不足以选择时，指出需要回到哪个日志缺口继续定位。

唯一收口可以是带条件的统一规则，例如按消费端修复状态决定是否采取生产侧适配或保留原配置。各条件分支必须有明确动作，不能留下互不关联的调查方向。

分析任务交付可执行的闭环方案；实际改代码、调整架构或升级系统按当前任务范围执行。说明原问题应如何被验证为恢复，并区分已执行结果与待执行方案。对用户确认的 golden example，直接采用已确认结果，不重新启动技术正确性审查。

实际项目中分别记录机制证据与交付决策：对照参数使功能恢复、用户决定正式采用该参数、具体失败机制获得动态证明，是不同事实。尊重已确认的交付选择，同时保留尚未完成的证据项；不能因参数被采用就宣称根因已证实，也不能因取证未完就否认用户已作出的产品决定。源码已修改、已上传、已构建、已部署及运行日志已命中也要分开记录，只将与本次实际运行版本相符的日志用于机制结论。

第五步的推进链为：

**最终准星 → 判断生产与消费关系中的问题机制 → 选择生产端修改或消费端处置 → 明确架构或版本条件 → 汇成回应原目标的唯一闭环动作。**

## 保留分支之间的推进关系

第零步至第五步规定推进次序，同时保留图中的跨领域连接。一个领域产生新证据后，回到它实际指向的领域或先前 Pending 的节点，写明哪项结果解除了什么限制、允许继续调查哪一段范围。沿用已确认的前序结果，不从头重走全部步骤，也不把局部解禁扩张成整个领域都值得深入。

收口时，将各支路的作用连回最终动作：哪些提供定位依据，哪些削弱候选解释，哪些确定适用条件，哪些因与当前目标关系不足而暂缓。必要条件仍未明确时，保留具体缺口；不要求把所有发散支路都调查到底。在必须交付的流程图中说明连线表示信号传递、假设关联、证据支持或调查依赖，不仅靠节点位置或颜色推断因果。

## 最后交付动作：输出调查流程图（每次必做）

将本次分析整理到可编辑的 `.drawio` 文件中，从左侧目标出发，展开四领域、观察与假设、测试及其结果、证据汇合与解禁、双焦点追踪及准星，最终连接右侧唯一收口。只填写当前材料实际支持的内容；未推进到的部分标明状态，不复制示例结论补齐流程。

交付前沿图检查：每个调查方向为何展开，每次跨领域推进由什么证据触发，各分支为何继续或暂缓，最终动作如何回应原目标。跳转缺乏依据时，回到对应缺口修正判断或标注未决，不能只补一条箭头制造合理性。

归档的 [assets/golden-example.drawio](assets/golden-example.drawio) 与 [预览](assets/golden-example.png) 是已确认案例的结构参照。新调查使用独立输出文件，保留归档原件；参考其分析组织方式，不继承其中的项目事实。具体输出位置、图面要求与交付检查见 [references/drawio-output.md](references/drawio-output.md)。

## 分析输出

围绕用户目标，给出：

首先交付本次可编辑 `.drawio` 文件及其链接，以下分析内容组织在图中，必要时辅以文字：

1. 目标问题及必要场景。
2. 常见噪声因素的判断与简短依据。
3. 四领域拆分：具体承担者或路径、源码/验证分类、当前已知信息。
4. 两个源码领域的 Pending 原因与解除条件。
5. 两个验证领域中可先推进的观察点，以及它们能够缩小哪部分不确定性。
6. 从初始化到结束或故障结果的动作过程、日志覆盖情况，以及问题动作的预期与实际表现。
7. 相关信号的消费链和调查来源，标出由问题动作推导出的重点区段、起止节点及映射依据。
8. 消费者终端的角色、裁决条件及其与目标外部表现的关系。
9. 从消费者终端由近到远排列的候选 Block 点，以及配置测试、实际变化和下一步调查方向；区分拟议测试与已执行结果。
10. 产生核心效果的配置改动、两端解除 Pending 的依据，以及双焦点 Trace 方案：生产端焦点、消费端两个副锚点和一个主锚点、轻负载路径日志方式、日志缺口与准星定位依据。
11. 最终准星所支持的修正方向、具体修改或处置对象、架构或版本适用条件，以及回应原目标的统一闭环动作。

在相应结果旁保留关键关系：线索为何进入主线、测试支持或削弱哪个假设、多项结果如何汇合、什么证据解禁了哪个领域。无需另造一份重复记录。

按当前已推进阶段输出有依据的结果，不将领域拆分、单个配置测试或诊断准备自动视为完成闭环。最终结论应能连回原目标，并由前面的动作观察、配置效果与双焦点定位说明其依据。

## Golden example：设备无法联网

用户已确认此案例正确，以下用于示范第零步至第五步的组织方式：

完整归档图：[assets/golden-example.drawio](assets/golden-example.drawio)；可直接查看的预览：[assets/golden-example.png](assets/golden-example.png)。

- 第零步：排除 Google 等防火长城因素的干扰。
- 生产终端节点：源头代码分析属于源码领域，改动通常很小，早期调查价值低时 Pending。
- 联网动作路径：Dmesg 与 TCPDump 分析属于验证领域，从实际联网行为寻找突破。
- 信号消费路径：梳理 CH397、USB 网络设备、ETH0、SKB、NAPI/GRO 到网络栈的链路，属于验证领域。
- 消费终端节点：OSKernel 内部分析属于源码领域，范围太大时 Pending，等待验证结果指向具体处理范围。

第二步先从初始化开始顺着 OS 日志观察联网执行过程，再结合 TCPDump 确认 DHCP 交互中的问题动作。图中从这个动作节点向下连接信号消费路径的若干节点，表达的是“动作焦点指向需要继续分析的消费区段”。据此查明相关报文的接收、交接和消费路径，将验证重点落到对应范围，而不是看到 DHCP 异常就直接把某个 SKB 函数认定为根因。

第三步以图中的 OS_Kernel_Net 为最终消费者锚点，从近端向上游回溯。先针对 NAPI/GRO 附近的候选原因关闭相关配置，表现没有变化；随后围绕 SKB 处理调整 copybreak，设置为 2048 后成功通网。这些测试体现的是由近到远试探候选 Block 点，并用结果决定继续排查还是聚焦该处理范围。

第四步在 copybreak 改为 2048 后通网这一核心效果出现时，解禁消费端 OSKernel 源码调查。回看生产端 CH397 驱动，其输入对照价值显现，也解除 Pending。准备双焦点日志：生产侧关注 ch397_rx_skb_fill() 中的数据构造与交接，消费侧关注图中的 packet_rcv() 及其相关消费位置。围绕同一条报文在两端的表现、配置改动前后的差异准备诊断。消费侧再按两个副锚点、一个主锚点、日志缺口组织追踪，不凭函数名预设其锚点类别或最终准星。

第五步沿最终准星追到 Linux 相关修复后，进入消费端版本调查，并形成图中右侧的统一规则：核实实际 Linux 修复状态；SKB 未修复的版本配置 RX_COPYBREAK 为 2048，已修复则保留 256。它将消费端版本条件与具体处置关联，统一回应设备联网目标。这是本案例已确认的规则，不将具体参数值泛化到其他问题。

案例中具体的网卡、日志工具和内核名称是领域实例，不是所有目标问题都必须使用的组件。复用的是从噪声排除、四领域发散，经验证与双焦点 Trace 确定准星，最终选择修正方向并收敛为唯一闭环动作的分析流程。
